Confirmed by reading the actual Terraform: this is a single aws_instance (t3.small, main.tf:175-209) — plain EC2, no ECS, no ASG, no standby replica. It's a genuine single point of failure today. No auto-recovery, no multi-AZ, nothing that respawns it if the instance or its AZ has a problem.

Concretely what that means in practice:

If the instance dies (host failure, AZ outage, someone terminates it) — super-admin dashboard access is down until someone manually re-runs terraform apply to recreate it. Since it holds a private_ip and an EIP association (lines 179, 212-216), Terraform will recreate it cleanly on re-apply and the fixed /32 stays the same (so the L3/L4/L7 allowlists don't need touching) — but that's a manual recovery step, not automatic failover.
Blast radius is contained, at least: it only fronts the admin-plane NLB (line 141-147 egress is scoped to the VPC CIDR), it's SSM-only (no SSH/keypair), IMDSv2-enforced, encrypted root volume. So a compromise or crash of this box doesn't take down the main product — it only takes down admin dashboard reachability, which is a real but bounded blast radius.
It's not resilience-engineered though. There's no CloudWatch alarm + auto-recovery action wired to this instance, no Auto Scaling Group with min=max=1 (which would at least get you automatic instance-replacement on failure without a human running Terraform), and no second gateway in a different AZ for actual HA.
Cheapest real fix if you want to close this gap without jumping to Verified Access: wrap it in an ASG with min_size=1, max_size=1 across two subnets/AZs (or just enable EC2 auto-recovery via a CloudWatch alarm on StatusCheckFailed_System), so a dead instance self-heals in minutes instead of waiting on a manual terraform apply. That's a small, additive change to this same module, not a redesign, and it directly answers your "not a single point of failure" concern for a lot less cost than Verified Access.
